# CodingWiki 总体架构（三阶段一体）

> 版本：v1.0（2026-10-30）
> 定位：**跨阶段唯一权威设计**。阶段一的实施细节见 `阶段1-总体架构.md`（含 §16 接口缝清单）；
> 业务目标与验收口径见 `docs/CodingWiki-项目开发计划.md` 第 5、6、13、14 章。
> 原则：三个阶段是同一条流水线的三段，不是三个项目。任何阶段的设计都必须回答「下一段怎么消费我」。
> 阅读入口：本目录 `README.md`（文档地图与阅读顺序）；三份阶段文档分别是 `阶段1/2/3-总体架构.md`。

## 1. 三阶段是一条闭环流水线

```text
外部需求文档 ──┐
               ▼
        ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
        │ 阶段二 Spec │───▶│ 阶段三 编码 │───▶│  代码变更    │
        └─────────────┘    └─────────────┘    └──────┬──────┘
               ▲                                     │
               │ 引用现状                             ▼
        ┌───────┴─────────────────────────────────────────┐
        │  阶段一：快照 → 事实 → Wiki → 索引 → 检索/问答   │
        └──────────────────────────────────────────────────┘
```

闭环的关键不是「二三阶段消费一阶段」，而是**三阶段的代码变更回流到一阶段**：

```text
编码合并 → 新 commit → repo sync（新快照）
        → 事实增量（blob 未变复用）→ Wiki 增量（PageDeps 比对）
        → 索引增量 → 评测回归 → 若指标下降则阻断
```

**这条回流路径当前完全缺失**（没有编排器把五步串起来，只能人工依次跑）。它属于阶段一的 `JobRunner`，也是二阶段能信任"Wiki 描述的是最新代码"的前提。

## 2. 统一实体与 ID 体系

跨阶段引用必须能反查到容器，否则追溯矩阵（13.7）无法机械校验。

| 实体 | ID 规则 | 阶段 | 说明 |
|---|---|---|---|
| 快照 Snapshot | `<repo_id>@<revision>` | 1 | 全项目唯一锚点，一切结论绑定它 |
| 符号 Symbol | `<path>::<qualified_name>@<line>` | 1 | 二阶段"代码位置"、三阶段"改动点"都用它 |
| 页面 Page | `<page_type>/<path>/<symbol>` | 1 | 二阶段读现状；页面内 `[E<n>]` 为局部号 |
| 切块 Chunk | `sha1(来源)[:16]` | 1 | 重建确定性一致 |
| 证据 Evidence | 页面内 `E<n>` | 1 | 只在页面容器内唯一 |
| 资料 Passage | 问答内 `S<n>` | 1 | 只在一次问答内唯一 |
| 需求 Requirement | `R-<spec_id>-<n>` | 2 | 跨容器唯一，可反查 Spec |
| 规格 Spec | `F-<yyyymmdd>-<seq>` | 2 | 绑定快照，快照变则整份 Spec 进入 stale |
| 任务 Task | `T-<spec_id>-<n>` | 2 | 三阶段的执行单位，可独立回滚 |
| 运行 Run | `RUN-<task_id>-<n>` | 3 | 一次编码循环；含构建/测试/修复轮次 |
| 补丁 Patch | `P-<run_id>` | 3 | 只允许改 Spec 白名单内文件 |

规则：

1. **局部号不跨容器**：正文里的 `[E1]`、`[S1]` 永不落盘为全局引用，落盘一律用全号。
2. **ID 里带父子关系**：`T-<spec>-<n>` 能反查 Spec，`RUN-<task>-<n>` 能反查任务；不引入独立自增全局序号（多机/多仓库会撞号）。
3. **任何跨阶段引用都要带快照**：`R1 @ S2` 表示"需求 R1 在快照 S2 下的现状"，避免 Spec 引用了过期事实（对应 13.7「代码位置必须在当前快照中存在」）。

## 3. 统一存储布局（`.codingwiki/`）

```text
.codingwiki/
├── repos/<repo>/work/                 # 工作树（materialize；三阶段另有 worktrees/）
├── worktrees/<task_id>/               # 三阶段：每任务独立工作树
├── snapshots/<repo>/<rev>.json
├── blobs/<sha[:2]>/<sha>              # 内容寻址
├── facts/<repo>/<rev>.json + latest + cache/
├── wiki/<repo>/{plans,drafts,versions,current}
├── indices/<repo>/<index_id>/{chunks.jsonl,vectors.bin,index.json} + current
├── jobs/<stage>/<repo>/<ts>-<id>/     # 统一任务包：stage = generate|ask|spec|code
├── specs/<repo>/<spec_id>/{spec.md,trace.json,state.json}
├── runs/<repo>/<run_id>/{patch/,build/,test/,report.json}
├── evals/<repo>/<eval_id>/{cases.jsonl,report.json}
└── locks/<repo>.lock
```

现状差异与处置：

| 差异 | 处置 |
|---|---|
| 任务包目前在 `wiki/<repo>/jobs/` | S7 改为 `jobs/<stage>/<repo>/`；旧路径保留只读兼容，不做破坏性迁移 |
| 无 `specs/`、`runs/`、`evals/`、`worktrees/`、`locks/` | 目录随阶段创建，命名规则先冻结（本节） |
| 无锁文件 | S10 落地；同仓同阶段串行，跨阶段可并行 |

## 5. 依赖规则（跨阶段）

```text
入口层      cli/  api/ 站点
编排层      pipeline/generate（1）· pipeline/spec（2）· pipeline/coding（3）· jobs（统一调度）
能力层      providers snapshot facts generate verify publish retrieval backends exec coding
基础层      config errors logging store
领域层      domain/（纯模型，无 I/O）
```

1. **只向下依赖**；跨阶段允许"上层编排同时调用两段能力"，但不允许能力层互相调用：
   - 二阶段可依赖 `facts/`、`publish`（读页面）、`retrieval`；不得依赖 `generate/` 内部实现；
   - 三阶段可依赖 `exec/`、`backends/`、`snapshot/`、`specs` 数据；**不得读 Wiki 文件结构**，只能通过 `WikiStore` API。
2. **阶段只通过「接口 + 落盘产物」通信**：二阶段读 `specs/` 落盘，三阶段读 Spec 文件而不是二阶段内存对象。
3. **领域模型统一基类**：当前 `domain/facts.py` 用 `_FactModel`、`domain/wiki.py`/`rag.py` 用 `_WikiModel`，两套配置重复。S7 合并为 `domain/base.py::CodeWikiModel`，二阶段 `domain/spec.py`、三阶段 `domain/patch.py` 直接继承，保证 `extra="forbid"` + `frozen=True` + 空白规范化全局一致。

## 6. 接口冻结策略

| 类别 | 内容 | 规则 |
|---|---|---|
| 冻结 | 快照 ID 与 blob 寻址、`SymbolFact` 定位字段、`TaskPacket`/`BackendResult` 契约、校验器只读原则、ID 命名规则（§2）、目录命名（§3） | 二三阶段不得修改；如需变更必须升主版本并全量回填 |
| 允许演进 | `SearchFilters` 字段、`Chunk.source_type` 取值、`PageType` 取值、`CommandRunner` 实现、`IndexMeta` 附加字段 | 加字段/加枚举值，不改语义 |
| 禁止 | 业务层 `new` 具体后端；索引里放模型私有字段；二阶段直接解析 Wiki Markdown 而非走 API；三阶段让模型执行命令（计划 14.3） | 违反即为设计缺陷 |

## 7. 当前实现与总体架构的差距（按阶段）

| 差距 | 影响 | 归属 |
|---|---|---|
| Cline 适配层缺失 | 二三阶段全部无法真跑，Wiki 只有模板文 | S8 |
| `CommandRunner` 缺失 | 三阶段无法构建/测试；一阶段也无法用构建验证事实 | S7 |
| 事实反查 API 缺失 | 二阶段影响分析无法机械化 | S7 |
| 检索无 filters | 二阶段范围检索、ACL 无法落地 | S7 |
| 无 worktree | 三阶段无法隔离任务 | S7 |
| stale/rollback 缺失 | 二阶段可能引用过期现状 | S7 |
| 无评测基线 | S6 换模型无法证明变好；三阶段回归无对照 | S9 |
| 无 JobRunner / 锁 | 回流闭环靠人工，日更不可用 | S10 |
| 无站点/看板 | 交付形态不完整（E7） | S11 |
| P4 未实现 | 7.9 前两条无法验收 | 待环境 |
| domain 基类重复 | 二三阶段模型风格漂移 | S7 |

## 8. 落地顺序（与阶段一 §16.7 一致）

```
S6   真实嵌入 + 重排（进行中）
S6.5 人可读交付：模块级页面体系 + 任务包改造 + ApiBackend + 静态站点 + 质量校验规则
S7   接口缝与统一基类：FactIndex 反查 / SearchFilters / CommandRunner / worktree / stale+rollback
S8   Cline 适配层（计划第 11 章 15 条验收）
S9   评测基线（金标准集：recall@k / 出处有效率 / 拒答准确率）
S10  JobRunner / 锁 / 回流闭环
S11  站点与覆盖率看板完善
P4   接入（依赖外部环境）
```

S7 先于 S8 的原因：二三阶段的每个组件都要落在 §4 的接口上；接口没冻结就先接真实模型，等于把返工成本转嫁到后两个阶段。
