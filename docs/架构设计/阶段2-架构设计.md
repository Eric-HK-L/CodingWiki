# 阶段二架构设计（Spec 生成）

> 版本：v0.7（2026-11-07）
> 定位：阶段二（开发 Spec 生成）的**实施基线**。目标与验收口径以 `docs/CodingWiki-项目开发计划.md` 第 13 章为准；一阶段实现与接口见 `docs/架构设计/阶段1-总体架构.md` v0.11。两者冲突时以计划文档为准。
> 状态：S12/S13/S14/S15/S16 已实现并合入 main（v0.7 补充并行轨道 S17 覆盖补强：接口页按目录聚合、流程页全量入口、页面依赖按作用域登记、旧页清理与页面上限调整）。
> 依据：计划 13.1–13.10、16.2 M4/M5、§4.3；一阶段验收报告 v1.1。

---

## 1. 目标与边界

把「需求文档 + Wiki + 代码事实 + 固定快照」变成可追溯到代码与测试的 Spec，状态机收口于 `approved`，供第三阶段消费。

边界（硬约束）：

- **不产补丁、不执行构建/测试、不改代码**（第三阶段）；
- 不替代产品/架构的最终决策，不自动批准；
- 首版只解析 Markdown 需求文档；不做 Web 评审界面；
- 不引入数据库/向量库（沿用文件索引 + 内存检索）。

---

## 2. 分层与依赖方向

```text
入口层   cli（codingwiki spec ...）
           │
能力层   spec/（ingest → evidence → impact → pipeline → validator → review）
           │ 只依赖下层，不反向
下层     domain/spec.py、domain/rag.py、facts/index.py、retrieval/search.py、
         backends/、providers/、pipeline/lock.py
```

规则：

1. `spec/` 不得 import `generate/` 与 `publish/` 的模块实现；需要「已有 Wiki 页」时，通过 `spec` 内定义的 Protocol（`WikiPageProvider`）注入，适配器在 `cli` 接线时构造。
2. `domain/spec.py` 为纯 Pydantic 模型：不读写文件、不打日志、不做 IO。
3. 校验器（`spec/validator.py`）为纯函数：输入 Spec/证据/事实索引，输出报告；不得修改任何文件。
4. 所有确定性计算（编号、覆盖比对、追溯、出处闭合、任务大小）不进模型；模型只负责抽取草拟、差距叙述、方案候选文字。

## 3. 领域模型（`domain/spec.py`）

| 模型 | 关键字段 | 不变量 |
|---|---|---|
| `SpecStatus` | `needs-info / draft / approved / rejected` | 状态只能按 §8 状态机流转 |
| `Requirement` | `id`（`R-*`）、`kind`（functional/non_functional）、`text`、`priority`、`acceptance: list[AcceptanceCriterion]`、`source_section`、`source_quote` | **`source_quote` 必须能在需求文档中定位**（逐字或规范化空白后匹配），否则视为编造，校验阻断；一条只描述一个可验证行为 |
| `AcceptanceCriterion` | `id`（`AC-*`）、`text`、`observable`（是否有可观察结果） | 每条功能需求至少 1 条 |
| `OpenQuestion` | `id`（`Q-*`）、`question`、`impact`、`owner`、`status` | `status != closed` 时 Spec 只能是 `needs-info` |
| `DesignTask` | `id`（`T-*`）、`goal`、`files: list[str]`、`estimated_lines`、`acceptance`、`depends_on` | `len(files) <= 3`、`estimated_lines <= 300`、单一目标 |
| `TraceRow` | `requirement_id`、`design_section`、`code_location`、`test`、`task` | 四列非空且引用可解析 |
| `SpecDocument` | `spec_id`（`F-*`）、`snapshot_id`、`source_doc`（路径+哈希）、`status`、`sections`（11 章）、`requirements`、`questions`、`tasks`、`trace` | 11 章不得静默缺失；元信息由系统写入，不采信模型输出 |
| `EvidenceItem` | `kind`（wiki/symbol/caller/config/build/test/similar）、`path`、`line`、`symbol_id`、`page_id`、`snapshot_id` | 每条证据可回到固定快照；`symbol` 类必须 `assert_symbol_exists` 通过 |
| `ValidationReport` | `blockers / warnings / info` | 任一 blocker 存在时不得进入评审 |

编号规则与一阶段对齐：`symbol_id = <path>::<qualified>@<line>`、`page_id` 为页面相对路径；Spec 侧用前缀 `F-/R-/N-/AC-/Q-/T-`，同一文档内稳定单调。

## 4. 需求文档接入（`spec/ingest.py`）

```text
需求 Markdown
  → 规范化（BOM/换行/空白、标题层级还原、去格式噪声）
  → 章节树（标题 + 起止行号）
  → 文档指纹 doc_sha256
  → 章节切块（source_type="doc"，携带 doc_id / section / 行号）
  → 进入检索索引
```

决策：

- `doc_id = <repo>@<doc_sha256>`；同一文档重复抽取得到相同编号序列（按章节顺序 + 局部序号，保证幂等）。
- 需求文档切块与代码块共用索引与 `SearchFilters`，通过 `source_types=("doc",)` 隔离；`Chunk.source_type` 从字符串扩展取值 `doc`，模型不变。
- `Chunk` 字段承载（S12 实测口径，不改模型）：
  - `page_id = doc_id`（文档级归属）；`title = 章节标题路径`；`start_line / end_line = 章节起止行`；
  - `file = 需求文档路径`；`trust_tier = fact`；
  - 索引构建时把 `snapshot_id` 统一覆盖为当前 facts 快照，避免旧抽取快照混入新索引。
- 文档更新后 `doc_id` 变化，旧 Spec 不自动改写；重新抽取生成新 Spec，旧 Spec 保留可追溯。
- 模型任务：抽取使用独立任务类型 `meta.json.task_type = "spec_extract"`，后端只写 `output/extract.json`；
  `spec/` 不感知 mock/api 差异，后端选择由 CLI 注入。

## 5. 证据与影响分析（`spec/evidence.py`、`spec/impact.py`）

每条需求的证据包（`evidence.json`）固定六类：

| 类 | 来源 | 用途 |
|---|---|---|
| wiki | 已发布页面（`WikiPageProvider`） | 现状与阅读路径（聚合页粒度，仅作导航） |
| symbol | `facts.index.symbol_by_id / symbols_in_module` + 名称/路径词元匹配 | 精确现状与签名 |
| caller | `facts.index.callers_of` | 影响分析的调用方 |
| config | `facts.config_facts` | 配置项新增/修改影响 |
| build | `facts.index.build_targets_touching` | 构建目标影响 |
| test | 构建目标关联测试 + 测试名匹配 + `tests_for_path` | 测试计划与回归范围 |

### 5.1 确定性检索口径（S13）

- 需求词元：`retrieval.tokenize` 对 `text + source_section + source_quote` 分词；ASCII 词元长度 ≥3 且去编程停用词，CJK 二元组用于 Wiki 匹配。
- 符号候选：先按词元倒排（名称/限定名/路径）计分，再对名称做子串匹配；按 `(得分, symbol_id)` 排序取前 8，禁止随机。
- **文档级兜底**：需求级匹配得不到任何 symbol/config/test 证据时，退到同一需求文档的全局词元（标题 + 全部需求）再匹配一次；仍为空则报错，不编造。
- 配置：键与路径分词后精确命中优先，ASCII 词元长度 ≥3 的子串命中次之，去重后取前 10。
- 构建：`build_targets_touching` 作用于已选符号所在文件。
- 测试：先取与构建目标 `target` 同名的测试，再按测试名/路径词元匹配；代码路径本身不是测试文件，不调用 `tests_for_path` 冒充关联。
- Wiki：只读 `WikiPageProvider`；页面 front-matter 的 `snapshot` 必须等于当前 facts 快照，过期页面不进入证据。
- 类似实现：与已选符号同名但位于其他模块的符号，按 `symbol_id` 去重取前 5。

### 5.2 产物 schema

```text
EvidenceBundle(repo_id, snapshot_id, doc_id, spec_id?, requirements[])
  └─ RequirementEvidence(requirement_id, items[EvidenceItem], impact)
       ├─ items: kind(六类), path, line, symbol_id, page_id, snapshot_id
       └─ impact: files, interfaces, callers, config, build, tests
```

- `files`：需改动的代码/配置文件（symbol 与 config 证据的 path）；
- `interfaces`：已选符号中 function/method/kernel/device_function 的 `symbol_id`；
- `callers`：调用方 `symbol_id`，无符号时用 `path:line`；
- `config/build/tests`：键名 / 构建目标名 / 测试名（`name` 或 `path`）。
- 无时间戳、无随机数：同输入同输出，可逐字节复算。

### 5.3 失败处理

| 情况 | 处理 |
|---|---|
| 某需求零证据（六类皆空） | `InputError`，列出需求编号，不产出「假完整」证据包 |
| `symbol` 证据不在快照 | `assert_symbol_exists` 抛错 |
| 非 symbol 证据路径不在 `facts.blob_by_path` | `InputError`，列出悬空位置 |
| Wiki 页面快照与 facts 不一致 | 丢弃该页面并计入警告，不冒充当前快照 |
| `--snapshot` 与 facts 快照不一致 | `InputError`，提示先做 facts extract |

拆分原则不变：确定性候选由 facts 直接产出；模型只负责差距叙述、类似实现选择与方案候选文字。每条「现状/影响」结论必须挂 `EvidenceItem`，无出处结论由校验器阻断。

## 6. 生成流水线（`spec/pipeline.py`）

```text
normalize → extract → evidence → draft → validate → persist
```

- 复用一阶段任务包与后端协议（`backends/protocol.py`：`TaskPacket` / `BackendResult`），`spec` 不感知 Cline/API/Mock 差异；
- 复用 S4 修复循环：校验 `blockers` 回喂模型，最多 3 轮；仍失败则保留草稿与错误清单，状态保持 `draft`，不产出「假完整」；
- 11 章模板渲染：无内容章节写「不适用」+ 原因；缺章节是 blocker；
- 方案设计：至少 2 个候选（需求确属唯一做法时写「唯一方案」并说明依据）+ 选择理由，决策写入 `decisions.md`（ADR 形式）；
- 成功产物：`spec.md`（人读）、`spec.json`（机读，二者同源渲染）、`evidence.json`、`validation.json`。

### 6.1 草拟契约（S14）

模型只写 `draft.json`，系统负责编号与元信息：

```json
{
  "sections": [{"number": 1, "title": "背景与目标", "body": "..."}],
  "tasks": [{"goal": "...", "files": ["a", "b"], "estimated_lines": 120,
             "acceptance": ["..."], "depends_on_indexes": [1]}],
  "trace": [{"requirement_id": "R-001", "design_section": "5 方案设计",
             "code_location": "path:line", "test": "...", "task_index": 1}],
  "decisions": [{"title": "...", "context": "...",
                 "candidates": [{"name": "...", "summary": "...", "pros": "...", "cons": "..."}],
                 "choice": "...", "rationale": "...", "unique_justification": ""}]
}
```

- `sections` 必须是 11 章、编号与标题与 `SPEC_SECTIONS` 完全一致；缺章/改标题为 blocker。
- `tasks` 由系统按顺序编号 `T-001…`；`depends_on_indexes` 为 1 起任务序号，系统转成 `T-*`。
- `trace` 的 `task_index` 同样由系统转编号；每条需求恰好一行，`code_location` 必须能对上一个 `EvidenceItem`。
- `decisions` 由系统编号 `D-001…`；`candidates` ≥2，确属唯一方案时用 `unique_justification` 说明；`choice` 必须是候选名之一。
- 需求、开放问题、快照、doc_id 一律来自 S12/S13 产物，模型不得新增或改写；模型新增的需求直接丢弃并记 blocker。

### 6.2 修复循环（S14）

```text
attempt 1..max_rounds(默认 3):
  backend.run(packet) → output/draft.json
  → 系统编号 + 组装 SpecDocument
  → validate_spec（结构规则 + S15 十项规则）
  → blockers 非空：errors.json 回喂下一轮
耗尽：保留 draft.json + validation-errors.json，抛出 InputError，不写 spec.md/spec.json
```

修复循环只修校验问题，不重跑抽取与证据（同输入证据固定）。Mock 故障注入 `spec_missing_section` / `spec_bad_task` / `spec_orphan_requirement` / `spec_orphan_task` / `spec_dangling_location` / `spec_unsourced_claim` / `spec_term_drift` / `spec_no_rollback` 用于测试。

### 6.3 落盘与状态（S14）

```text
.codingwiki/specs/<repo>/<spec_id>/
  spec.json / spec.md / evidence.json / validation.json / decisions.md
  draft-task/（任务包与 output/draft.json，审计用）
```

- `status`：存在未关闭 `Q-*` → `needs-info`，否则 `draft`；`approved` 只由 S16 写入。
- `validation.json` 是 S14 结构校验报告；S15 在其上扩充十项规则，契约不变。
- `spec.md` 与 `spec.json` 同源：先组装 `SpecDocument`，再由模板渲染 Markdown。

## 7. 自动校验器（`spec/validator.py`）

`validate_spec(spec, extraction, evidence) -> ValidationReport` 为纯函数，不读写文件、不调用模型。计划 13.8 十项检查与 13.7 追溯规则映射如下；规则 ID 即报告中的 `SpecIssue.rule`，修复循环按 `ref` 回喂。

| # | 检查 | 规则 ID | 判定口径 | 级别 |
|---|---|---|---|---|
| 1 | 需求覆盖 | `requirement_coverage` | 抽取产物与 Spec 的需求编号集合必须完全一致；模型新增/遗漏均阻断 | blocker |
| 2 | 验收标准 | `acceptance_criteria` | 每条功能需求 ≥1 条 `AC-*` | blocker |
| 3 | 代码出处 | `code_source` / `trace_location` | 第 3、6 章正文中以反引号给出的代码/Wiki 位置必须命中证据包；追溯行 `code_location` 必须回指证据 | blocker |
| 4 | 追溯完整 | `trace_completeness` | 每条需求恰好一行；每个任务至少被一行引用；引用的需求/任务必须存在 | blocker |
| 5 | 任务大小 | `task_size` | 模型层 ≤3 文件/≤300 行；校验器复核依赖存在、编号唯一 | blocker |
| 6 | 测试计划 | `test_plan` | 每条功能需求在第 7 章出现且追溯行有测试；无测试证据时显式标注「待补充」记 warning（由 S16 人工评审收口） | blocker / warning |
| 7 | 开放问题 | `status_questions` | 有未关闭 `Q-*` 时状态只能是 `needs-info`；`draft`/`approved` 下有未关闭问题即阻断 | blocker |
| 8 | 术语一致 | `term_consistency` | 以证据中的符号名/配置键/构建目标/测试名为术语表；Spec 正文出现大小写或拼写漂移即阻断 | blocker |
| 9 | 安全 | `security_review` | 涉及输入/权限/配置的需求（影响面有 config 或正文命中关键词）时，第 9 章须出现「安全」 | warning |
| 10 | 回滚 | `rollback` | 第 9 章必须出现「回滚」步骤 | blocker |

补充规则（不属 13.8 十项，但为闭环必需）：

| 规则 ID | 判定 | 级别 |
|---|---|---|
| `section_structure` | 11 章齐全、编号与标题与 `SPEC_SECTIONS` 一致 | blocker |
| `evidence_coverage` | 证据快照与 Spec 快照一致、每条需求有证据包、证据条目快照一致 | blocker |
| `decision_present` | 至少一条方案决策；候选与选择由模型不变量保证 | blocker |
| `task_scope` | 任务 `files` 必须来自该需求的证据影响面或证据路径 | blocker |
| `status_integrity` | 状态为 `approved` 时现场重算不得有 blocker；`approved` 不得有未关闭问题 | blocker |

分级纪律：

- `blockers`：必须修复，修复循环回喂；耗尽不落盘 `spec.json`；
- `warnings`：建议修复，不阻断生成，但 S16 `approved` 前须由评审人确认（如无测试证据的「待补充」、安全段缺失）；
- `info`：供评审参考（如未关闭问题数量、快照变更提示）。

`test_plan` 采用「需求级映射」首版口径：一条功能需求的追溯测试覆盖其全部 AC。AC 级测试映射需要扩展草拟契约（`AC-* → test`），留到 S16 试点后再定，避免 S15 改动 draft schema 导致修复循环不可控。

CLI `codingwiki spec validate <spec_dir>`：读取 `spec.json` + 同目录 `evidence.json`，抽取产物优先取 `draft-task/context/extract.json`，其次按 `evidence.repo_id + source_doc.doc_id` 找 `docs/<doc_id>/extract.json`；无 blocker 返回 0，有 blocker 返回 3，输入不可读返回 2。校验器本身只读，不覆盖已落盘 `validation.json`。

## 8. 评审状态机（`spec/review.py`）

```text
（抽取）
   └─→ needs-info ──关闭全部 Q──→ draft ──评审通过（blockers=0）──→ approved
                                     │                              │
                                     └──评审退回──→ rejected         └──→ rejected（保留原因）
```

- 评审角色（计划 13.9）：`requester` 需求提出人、`module_owner` 模块负责人、`test_owner` 测试负责人、`security` 安全/合规、`architect` 架构师；角色用稳定英文枚举值，CLI 展示中文名。
- 评审结论：`approve` / `reject`；`reject` 必须填写意见（原因不得丢失）。
- 评审记录 `ReviewRecord`：`spec_id`、`role`、`decision`、`comment`、`created_at`（ISO 8601 UTC，唯一非确定性字段）、`snapshot_id`、`blockers`、`warnings`、`warnings_acknowledged`；`approve` 记录的 `blockers` 必须为 0（模型不变量）。
- `review.json` 为 `ReviewLog`：`spec_id`、`snapshot_id`、`reviews[]`（按时间追加，不覆盖历史）；与 `spec.json` 同目录、同快照。
- 状态迁移由系统执行，禁止手改 `spec.json` 的 `status`：
  - `needs-info → draft`：全部 `Q-*` 关闭后才允许；S16 通过 `spec review --close-question Q-001` 显式关闭（记录到评审意见）；
  - `draft → approved`：`spec validate` 现场重算 `blockers = 0`、无未关闭 `Q-*`、评审记录落下；有 `warnings` 时必须 `--ack-warnings` 显式确认并写入记录；
  - `draft/needs-info/approved → rejected`：必须有 `--comment`，保留原因；
  - `approved` 不再接受模型自动改写；修改须回到 `draft` 重新评审（S16 不做自动回退，重建 Spec 即可）。
- 快照一致：评审时 `spec.snapshot_id`、`evidence.snapshot_id` 必须一致；不一致按输入错误拒绝，不静默评审过期 Spec。
- 门禁失败（blockers、未关问题、未确认 warnings、非法迁移、快照不一致）退出码 3；文件不可读/参数错误退出码 2；成功 0。

CLI：

```text
codingwiki spec review <spec_dir> --approve --role module_owner --comment "..."
codingwiki spec review <spec_dir> --approve --role architect --ack-warnings
codingwiki spec review <spec_dir> --reject --role test_owner --comment "测试计划不可执行"
codingwiki spec review <spec_dir> --approve --role requester --close-question Q-001 --comment "阈值已确认 3dB"
```

`review.py` 分层：

| 函数 | 职责 | 副作用 |
|---|---|---|
| `review_spec(spec, report, log, *, role, decision, comment, close_questions, ack_warnings, now)` | 纯函数：门禁校验 + 迁移状态 + 追加记录 | 无 |
| `load_review_log(directory)` / `save_review_log(log, directory)` | 读写 `review.json` | 文件 IO |
| `apply_review(...)` | 调纯函数后同源写回 `spec.json` / `spec.md` / `review.json` | 文件 IO |

`approved` 的完整性由两层保证：模型不变量（`approved` 不得有未关闭问题、`validation.blockers` 必须为空、approve 记录 blockers=0）+ 校验器 `status_integrity`（现场重算发现 blockers 而状态为 approved 即阻断）。

## 14. 关键约束与已知坑

1. **模型编造需求**：靠 `source_quote` 可定位性阻断；模型输出的每条需求都必须能回指原文。
2. **聚合页覆盖不足**：证据以 facts 为主，Wiki 页只作导航；S17 补强后再提升页面引用比例。
3. **Spec 与快照脱节**：所有证据带 `snapshot_id`；换快照后旧 Spec 标记「现状可能过期」，不静默沿用。
4. **任务包过大**：任务大小 blocker 前置，避免把「不可编码」的大任务带到第三阶段。
5. **mock 后端误用**：mock 仅用于链路测试与故障注入，不得用于试点指标；指标必须来自真实模型。
6. **状态机被绕过**：`approved` 只能由 `spec review` 写，且校验 blockers=0；禁止手工改 `spec.json` 的 status（校验器 `status_integrity` 现场复核）。

## 15. 并行轨道 S17：覆盖补强与新鲜度复测（v0.7 新增）

### 15.1 目标与批量顺序

把一阶段移交的覆盖率目标（C1 ≥95%、C2 ≥95%、C3 ≥80%）落到页面体系，不阻塞 Spec 主线：

```text
C3 流程页：入口按目录去重后全量成页（最多 120 页）
  → C2 接口页：按目录聚合公开符号，取公共符号累计 ≥95% 的目录
  → C1 文件说明：页面 deps 登记作用域文件，模块页覆盖其全部文件
  → 每批：wiki coverage + eval(cuphy-v2) delta 回归
```

### 15.2 页面粒度调整

| 页面类型 | 一阶段（v0.6 及以前） | S17（v0.7） | 理由 |
|---|---|---|---|
| 接口页 | 按头文件，最多 24 页 | **按目录聚合**，取公共符号累计覆盖 ≥95% 的目录（最多 100 页） | 单文件一页需要 338 页才能到 95%，目录聚合 42 页即可；组件级接口页更可读 |
| 流程页 | 按入口文件，最多 12 页 | **按入口目录去重后全量**（cuphy 93 页，上限 120） | C3 分母就是「目录去重入口」，一页只能覆盖一个入口文件 |
| 模块页 | 按目录，≤60 页 | 不变（仍按目录聚合 + 补遗页） | 模块页是 C1 的聚合载体 |

页面规划仍是确定性规则（`generate/plan.py`），模型不决定写哪些页。

### 15.3 页面依赖（`PageDeps.files`）登记口径

一阶段的 deps 只记录证据文件，导致「模块页覆盖模块但 C1 只算证据」的低估。v0.7 起 deps 登记**页面作用域**：

| 页面类型 | deps.files |
|---|---|
| 模块页（含补遗页） | 该模块/补遗范围的全部文件 |
| 接口页 | 该目录下全部文件（含无公开符号文件） |
| 流程页 | 入口文件 + 流程步骤触达文件 |
| 系统/配置/构建/测试/术语页 | 证据文件（作用域为全仓，不额外登记） |

语义：deps 既是覆盖登记，也是增量复用与 stale 判定依据——作用域内任一文件变更都应触发该页再生成。C1 的分子因此等于「被页面作用域覆盖的文件」，与一阶段决策的聚合页口径一致。证据仍只来自任务包预提取的 E 编号，不因 deps 扩大而放宽出处校验。

### 15.4 页面上限与发布门禁

`publish/store.py` 的 `check_gate` 上限随粒度调整：模块 60、接口 100、流程 120、总页数 300。超出即拒绝发布（防止规则失控），但不再用一阶段 50–120 的裁剪区间限制 S17 的聚合页总量。

### 15.5 旧页清理

接口页从「按文件」改为「按目录」后，旧 page_id 会残留在草稿区并被发布。规则：**全量计划生成时（`max_tasks=0`），删除不在当前计划内的草稿页**；增量生成（`max_tasks>0`）不清理，避免把预算外页面误删。CLI `wiki generate` 与 `codingwiki run` 的 wiki 阶段都走该规则。

### 15.6 门禁与验收

1. 每批扩页后跑 `codingwiki wiki coverage --repo cuphy`，记录 C1/C2/C3 与页面总数；
2. 跑 `codingwiki eval --repo cuphy --golden evals/golden/cuphy-v2.yaml`，四项指标与基线 delta 对比，明显回退（Recall/出处/拒答任一 >5 个百分点）即回退该批；
3. 发布门禁、出处校验、stale/rollback 机制不变；
4. 新鲜度：cuphy 出现新 revision 后跑 `codingwiki run --repo cuphy`，记录受影响页从 sync 完成到重新发布的耗时；无法获得新 revision 时，用本地 worktree 合成变更并如实标注为「合成变更实测」。
