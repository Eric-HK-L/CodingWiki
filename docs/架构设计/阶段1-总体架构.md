## 1. 设计目标与约束

目标：在阶段一交付“可日更、可检索、可溯源”的 Repo Wiki。

约束：

- 公司内模型调用只能走 Cline headless；不能 MCP/ACP；不能外部模型；不能本地生成模型；
- 分析必须“先事实、后叙述”，事实由确定性工具产出，模型只写解释；
- 一切结论绑定不可变快照，出处可机械校验；
- 开发机只在工作区内落文件（见计划文档 20.1）；
- 每个小阶段独立分支、PR、合并，代码与测试同步交付。

## 2. 分层与依赖方向

依赖只能从上往下，**下层不能 import 上层**；同一层之间通过接口（Protocol）解耦，不直接 import 具体实现。

```
┌──────────────────────────────────────────────┐
│ 入口层    cli/  api/            （命令与 HTTP） │
├──────────────────────────────────────────────┤
│ 编排层    pipeline/             （任务编排、状态机）│
├──────────────────────────────────────────────┤
│ 能力层    providers/ snapshot/ facts/          │
│           generate/ verify/ publish/          │
│           retrieval/ backends/                 │
├──────────────────────────────────────────────┤
│ 基础层    config/ errors.py logging_setup.py store/ │
├──────────────────────────────────────────────┤
│ 领域层    domain/               （纯数据模型，无 I/O）│
└──────────────────────────────────────────────┘
```

规则：

1. `domain/` 只放 Pydantic 数据模型、枚举、纯函数；不读写文件、不发网络请求、不打日志。
2. `config/` 负责“文件 → 已校验的对象”，不感知业务语义。
3. `providers/` 只负责“取代码”，不解析代码。
4. `facts/` 只产出事实，不生成文字。
5. `generate/` 只负责“把事实与约束打包给模型，把模型输出解析回结构化结果”，不做事实提取。
6. `verify/` 只做校验，不改内容。
7. `publish/` 只做版本切换与存储，不生成内容。
8. 入口层只做参数解析、错误转退出码、调用编排层。

## 3. 核心接口

接口先定形，实现按阶段补齐；接口一旦定型，改动必须同步改本文档与对应 ADR。下面把完整 Protocol 列出，方便后续阶段对齐签名。

### 3.1 代码源（S2 实现）

```python
class SourceProvider(Protocol):
    """统一接口：GitHub / GitLab / Gitea 都能包装成同一套方法。"""
    name: str                     # "git" / "p4"
    def latest_revision(self, repo: RepoConfig) -> str: ...
    def materialize(self, repo: RepoConfig, revision: str) -> Path: ...
    def changes(self, repo: RepoConfig, old: str, new: str) -> ChangeSet: ...
    def read_file(self, repo: RepoConfig, revision: str, path: str) -> bytes: ...
    def metadata(self, repo: RepoConfig) -> RepoMetadata: ...
```

`ChangeSet`：`added: list[str]`、`modified: list[str]`、`deleted: list[str]`、`renamed: list[tuple[str,str]]`、`binary_changed: list[str]`，外加 `old_revision`、`new_revision`。

### 3.2 快照（S2 实现）

```python
class SnapshotStore(Protocol):
    """快照 = 不可变版本号 + manifest（路径/哈希/语言/大小/排除标记）。"""
    def create(self, repo_id: str, revision: str, workdir: Path, provider: str) -> Snapshot: ...
    def manifest(self, snapshot_id: str) -> Manifest: ...
    def latest(self, repo_id: str) -> Snapshot | None: ...
    def diff_manifests(self, old_id: str, new_id: str) -> ChangeSet: ...
    def read_file(self, snapshot_id: str, path: str) -> bytes: ...
```

### 3.3 事实层（S3 实现）、Wiki 生成（S4）、检索（S5）

```python
class FactExtractor(Protocol):
    def extract(self, snapshot: Snapshot, workdir: Path) -> RepoFacts: ...

class FactStore(Protocol):
    """事实按快照落盘；未变化的文件按 blob_sha256 复用解析结果。"""
    def save(self, facts: RepoFacts) -> Path: ...
    def load(self, repo_id: str, revision: str) -> RepoFacts | None: ...
    def latest(self, repo_id: str) -> RepoFacts | None: ...

class ModelBackend(Protocol):
    def run(self, package_dir: Path, timeout_s: int) -> ModelResult: ...

class PageStore(Protocol):
    def stage(self, pages: list[Page], snapshot_id: str) -> str: ...
    def publish(self, version: str) -> None: ...

class Retriever(Protocol):
    def search(self, query: str, filters: SearchFilters, top_k: int) -> list[Passage]: ...
```

## 4. 数据流（阶段一）

```
取代码 → 快照（manifest） → 事实提取 → 覆盖计划 → 任务包
      → 模型生成 → 校验 → 修复重试 → 发布（版本切换）
      → 切块索引 → 混合检索 → 问答
```

每一步都落盘、可重放：同一步骤输入相同，输出应可复现（模型步骤除外，记录输入输出哈希）。

### S2 数据流细节

```
RepoConfig (YAML)
  → GitProvider.materialize(revision)  # clone/fetch + worktree 固定到某 SHA
  → SnapshotStore.create(repo_id, revision, workdir)
    1. 遍历 workdir，计算 sha256（内容寻址），按 7.5.1 规则判断是否排除
    2. 语言识别（扩展名 + 文件头）
    3. 大文件默认只记录元数据（≥ 2 MB）
    4. 生成 Manifest（JSON）
    5. 文本文件内容入 BlobStore（可选，为事实层预热）
    6. 落盘快照元数据（snapshot.json）
  → SnapshotStore.diff_manifests(old, new)  # 新增/修改/删除/重命名/二进制变化
```

### S3 数据流细节

```
Snapshot (manifest) + workdir
  → 逐文件解析（tree-sitter：C / C++ / CUDA / Python）
    1. 未变化文件按 blob_sha256 命中缓存，直接复用 FileFacts
    2. 符号 / include-import / 直接调用 / 入口 / 宏 / CUDA 标记
  → 构建发现（CMakeLists 文本解析 + compile_commands.json + CMake File API reply）
  → 配置发现（YAML/JSON/TOML 键 + 代码内环境变量与 CLI 参数读取）
  → 测试发现（gtest 宏 / pytest 函数 / ctest add_test）
  → 符号索引 → 调用目标解析（同文件优先、全库唯一名次之）
  → 质量报告（解析成功率、未解析调用比例、构建/配置/测试覆盖）
  → FactStore.save()  # .codingwiki/facts/<repo_id>/<revision>.json
```

## 6. 错误模型与退出码

统一异常基类 `CodingWikiError`，子类分成四类，决定是否重试：

| 类别 | 例子 | 处理 |
|---|---|---|
| 用户/输入错误 | 配置格式错、路径不存在、参数非法 | 不重试，直接给出可操作提示 |
| 环境错误 | 命令不存在、磁盘满、权限不足 | 不重试，提示修环境 |
| 可重试错误 | 网络超时、模型进程超时、锁冲突 | 有上限重试，记录次数 |
| 内部错误 | 断言失败、未处理异常 | 不重试，记录并告警 |

CLI 退出码：`0` 成功；`2` 输入/配置错误；`3` 环境错误；`4` 可重试错误耗尽；`1` 内部错误。

### 11.1 S2 设计要点

- **先写 Protocol、再写实现**：`providers/protocol.py` 和 `snapshot/protocol.py` 单独放，实现文件只 import 它们。
- **materialize 用 git worktree**：bare 仓库 + worktree 固定到某 SHA，省磁盘且天然隔离。
- **manifest 是权威**：`GitProvider.changes()` 用于跨版本触发，但 `SnapshotStore.diff_manifests()` 才是最终变更清单。
- **排除每条都写原因**：不是"假装不存在"，manifest 里标记 `excluded: true` 并写 `exclusion_reason`。
- **语言识别保守**：扩展名优先，其次文件头；识别不出来标记 `unknown`，不瞎猜。
- **二进制检测保守**：扩展名在名单内直接标记；其他用 null-byte 检测辅助。
- **大文件默认截断**：manifest 里标记 `truncated: true`，事实层和生成层自动跳过。
- **快照 ID 可预测**：`<repo_id>@<sha>`。
- **同一仓库串行**：`.codingwiki/locks/<repo_id>.lock`，防止两个任务同时写同一快照。

### 12.1 S3 设计要点

- **语法级优先，语义级留后**：tree-sitter 不依赖编译环境，可在任意仓库上跑；`compile_commands.json` 只用于统计覆盖率和后续升级，不在此阶段做类型推断。
- **每条事实带 `confidence`**：tree-sitter 结构 = high，CMake 文本解析 = medium，正则扫描 = low；`source` 用 `file:line`。
- **CUDA 不是普通 C++**：tree-sitter-cpp 会把 `__global__` 解析成 ERROR 节点，因此核函数/设备函数用"函数定义前的前缀文本"标记；`<<<...>>>` 启动用正则识别并记 `kind=kernel_launch`。
- **解析失败不静默**：`FileFacts.parse_ok=false` + `parse_errors` 计数；质量报告给出解析成功率。
- **缓存按内容哈希**：`facts/<repo>/cache/<extractor_version>/<sha>.json`；解析器逻辑变更时升 `EXTRACTOR_VERSION`，旧缓存自然失效。
- **调用解析保守**：先同文件唯一名，再全库唯一名；仍不唯一则保留未解析，计入未解析比例，不猜。
- **构建目标不虚构**：CMakeLists 只解析显式命令；动态生成的源文件列表无法还原时标记 `confidence=low` 并在备注里说明。
- **入口只认确定的形态**：C/C++ 的 `main`、CUDA 启动、Python `__main__` 与 argparse 子命令；不猜测"可能是入口"的函数。

## 13. S4 范围：Wiki 生成、校验与发布

对应计划文档第 9 章与第 11 章。核心原则：**证据由确定性程序从快照预提取并编号，模型只能在给定证据间做“结论-证据映射”**；校验器不调用模型，只做机械核对；发布走版本目录 + 门禁，失败不覆盖旧版。

做：

- `domain/wiki.py`：`PageType` / `CoverageLevel` / `PageStatus` / `PageMeta`（front matter）/ `Claim` / `Evidence` / `UnknownItem` / `PageResult`（result.json 契约）/ `Page` / `PageTask` / `CoveragePlan` / `PageDeps` / `VerifyIssue` / `VerifyReport` / `VersionIndex`；
- `backends/`：`ModelBackend` Protocol（计划文档 11.3）+ `MockBackend`（确定性生成，可注入故障模拟修复循环）；`ClineHeadlessBackend` / API 后端只留配置与接口，S4 不实现真实调用；
- `generate/`：`CoveragePlanner`（覆盖计划）→ `TaskPackageBuilder`（任务包 + 证据预提取）→ `ModelBackend.run` → `ResultParser` → `Verifier` → 修复循环（≤3 次）→ stage 草稿；
- `verify/`：`PageVerifier`（格式/结构/证据/语义/内容五组规则）；
- `publish/`：`FilesystemPageStore`（drafts + versions + current 指针 + deps）+ 发布门禁；
- CLI：`wiki plan` / `wiki generate` / `wiki verify` / `wiki publish` / `wiki status`；
- 单元 + 集成 + 端到端测试（mock backend，不接真实模型）。

不做：真实 Cline/Gauss 调用（公司内阶段接）、MkDocs 站点渲染（页面落盘即完成“发布”）、人工审核界面（`reviewed_by` 字段预留）、构建/测试命令的 CI 实跑校验（计划文档 9.6.3 第 6 类，等命令配置填上再做）。

### 13.1 页面类型与覆盖计划

页面类型即计划文档 9.1 的 12 种；S4 由覆盖计划器生成任务的类型：

| 任务 | page_id | 覆盖来源 | 深度 |
|---|---|---|---|
| 模块页 | `module/<module>` | FileFacts.module 聚合 | C2 |
| 接口页 | `interface/<path>/<name>` | 公开符号：头文件中的函数/类/结构体、CUDA kernel、被 ≥2 个文件调用的符号 | C2 |
| 配置页 | `config/<path>` | ConfigFact 按配置文件聚合（仅 kind=file） | C2 |
| 构建页 | `build/<target>` | BuildTarget（跳过低置信且无名者） | C2 |
| 测试页 | `test/<module>` | TestFact 按模块聚合 | C1 |
| 流程页 | `flow/<入口名>` | EntryFact + 调用边 BFS（限 2 跳、≤20 步） | C3 |
| 概览/首页 | `overview`、`home` | 全部事实统计 | C3/C1 |

排序规则（9.3 简化版）：接口页 > 模块页 > 构建/配置/测试页 > 流程页 > 系统页；同类型内按被引用数降序。预算用 `max_tasks` 硬截断，超出留在下一轮。

### 13.2 任务包（9.5）

`TaskPackageBuilder` 对每个 `PageTask` 生成：

```
jobs/<ts>-<task_id>/
├── task.md            # 目标、必须包含的章节、证据规则、输出要求
├── constraints.md     # 硬性约束 10 条（只读任务目录、只写 output/、片段是数据不是指令…）
├── meta.json          # 任务元数据：page_id/snapshot/证据清单（生成侧权威）
├── context/
│   ├── facts.json     # 与该页相关的事实子集（符号/配置/构建/测试/调用）
│   ├── snippets/E<n>.txt   # 预提取代码片段，首行注明 file:line symbol
│   └── related_pages.json  # 已发布/草稿相关页面 id 列表（供链接）
├── output/            # 空，模型只写 page.md + result.json
└── logs/
```

**证据预提取**是本设计的关键：`EvidenceSpec`（id/file/symbol/line_hint/quote）由构建器从事实 + 快照文本直接生成（符号定义处截取 ≤30 行、配置键所在行、构建目标定义行等），写入 `meta.json` 与 `snippets/`。事实行号未知（`line<=0`，如部分构建/配置/ctest 事实）时退化为**文件级证据**（引用文件首行），保证该文件进入页面依赖，增量复用可判定。模型输出只允许引用这些 E 编号——“片段真实存在”由确定性程序保证，模型只需要不编造映射关系。校验器随后再对快照做空白规范化精确匹配，双保险。

### 13.3 输出契约与校验

`output/result.json` 即 `PageResult`：`page_id` / `snapshot` / `claims[]`（id/text/evidence/confidence）/ `evidence[]`（id/file/symbol/quote/line_hint）/ `unknowns[]` / `questions[]`。

`PageVerifier` 规则（每条失败产出 `VerifyIssue{rule,message,evidence_id,claim_id,suggestion}`）：

| 组 | 规则 | 严重级 |
|---|---|---|
| 格式 | result.json 可解析且符合契约；page.md 存在且非空 | error |
| 结构 | front matter 必填字段齐；id/type/snapshot 与任务一致；status 合法 | error |
| 证据 | 页面 `[En]` ↔ result.claims ↔ result.evidence 三方编号闭合一一对应；evidence.id 必须出现在任务包 meta.json 中；quote 空白规范化后在快照文件精确匹配（多处匹配用 line_hint 取最近）；symbol 非空时须在事实库存在 | error |
| 语义 | 接口页 evidence 的符号签名与事实库一致（quote 中包含解析签名关键子串）；配置页键名在事实库存在 | error |
| 内容 | 无“大概/可能/应该是/也许/据说”等无依据模糊词；内部链接目标在已知页面集合内；正文字数 200–8000 | 模糊词 error，链接/字数 warning |

校验报告落盘 `VerifyReport{page_id,status,issues,checked_at,verifier_version,page_sha256,result_sha256}`；两个哈希绑定“通过校验的确切内容”。失败时写 `errors.json` 进下一轮任务包，修复循环最多 `max_rounds=3` 次；仍失败页面标 `failed`，**不进入草稿区覆盖旧页面**（9.8.3）。

### 13.4 MockBackend

开发与 CI 不依赖真实模型（计划文档 11.3）。`MockBackend` 读任务包后**纯模板化组装**页面：结论全部来自 context/facts.json 的事实字段（签名、配置键、构建目标、测试名、调用边），每条结论挂对应 E 编号；同步生成 result.json（claims/evidence 与 meta.json 一致）。它代表“生成质量地板”——真实模型只会写得更多，不会绕过校验。

故障注入用于测试修复循环：`MockBackend(fail_rounds=[{"rule":..., ...}])` 前 N 轮输出坏结果（如引用不存在的 E99、缺 front matter 字段），第 N+1 轮恢复正常。

`ModelBackend` Protocol 按计划文档 11.3：`run(packet: TaskPacket) -> BackendResult`；`TaskPacket{workspace,task_file,output_dir,timeout_s,metadata}`；`BackendResult{status,exit_code,output_files,stdout,stderr,duration_ms,tokens_in,tokens_out,model,error}`。

### 13.5 发布与增量

`FilesystemPageStore`：

- stage：`drafts/pages/<page_id 转路径>.md` + 同名 `.result.json` / `.verify.json` / `.deps.json`；
- 依赖记录 `PageDeps{files:[{path,blob_sha256}], symbols, evidence_ids, prompt_version, backend, model}`（9.10.1）；依赖文件取自任务包证据引用的文件，blob 哈希来自 `RepoFacts.blobs`（快照全量在范围文件，含 CMake/配置等非代码文件）；
- publish：`versions/<version_id>/pages/...` 复制全部 verified/draft 页面 + `index.json`（页面清单、状态统计、快照），门禁通过后原子写 `current`；`version_id = v<yyyymmddHHMMSS>-<revision[:8]>`；
- 门禁（9.12.3）：版本内无 `failed` 页面、全部页面 verify=passed、**草稿内容与通过校验时哈希一致（防复验后篡改）**、版本内内部链接全有效、证据有效率 100%。门禁不过则发布中止，保留旧 `current`；
- 增量（9.10）：新事实就绪后重跑 `wiki plan`；计划器读 drafts 的 deps，比对页面依赖文件的 blob 哈希/符号签名哈希，未变化页面直接复用（`reuse` 标记），受影响页面重新生成；代码已变但页面未更新的标 `stale`。

## 14. S5 范围：RAG 检索与问答

目标（计划文档第 10 章）：在本地交付**搜索模式**（不依赖模型，必须始终可用）与**问答模式**（经 ModelBackend 协议，答案带可校验出处、资料不足可拒答）。

阶段一对第 10 章的裁剪：

| 计划文档 | 阶段一做法 | 原因 |
|---|---|---|
| 10.4.1 嵌入模型选型（BGE-M3 等） | `EmbeddingBackend` Protocol + 内置 `HashEmbedding`（词元哈希投影，确定性、零依赖）；真实模型实现留后续 | 嵌入模型选型需要金标准集评测（10.9），是独立工作；协议先行，实现可换 |
| 10.4.4 pgvector | 本地文件索引（chunks.jsonl + vectors.bin），查询时内存计算 | 阶段一无外部服务依赖；切块万级规模纯 Python 足够 |
| 10.5.3 学习式重排 | 确定性重排：RRF 融合 + 标识符精确命中/信任层级加权 | 重排模型同属评测选型工作 |
| 10.7 权限 ACL | 不做；单用户本地 CLI | 权限是部署形态问题，留第二阶段 |
| 10.9 金标准评测 | 测试内小型金标准断言 Recall@10；评测 harness 留后续 | 金标准集需要多人标注流程 |
| 10.10 网页/HTTP/IDE | 只做 CLI：`index build` / `search` / `ask` | 阶段一服务形态就是命令行 |

### 14.1 切块（Chunk）

`Chunk{chunk_id, source_type, repo_id, snapshot_id, file, symbol, module, title, text, start_line, end_line, trust_tier, page_id}`。`chunk_id` 确定性生成（来源 + 路径 + 行范围哈希），同一快照重建结果一致。

三类来源（信任层级 10.2）：

- **代码块（T3）**：以符号为单位（`SymbolFact.line..end_line` 从快照文本截取），含路径/符号名/签名/函数体；超长按 1200 词元近似值折行切分并保留重叠；构建目标、配置键、测试用例各成小块（同时承担 T2 角色）；
- **Wiki 块（T1）**：当前发布版本的页面按标题层级切分，块保留页面 ID 与标题路径；页面不存在时该来源为空；
- 事实块不单独建：符号签名已在代码块文本中，T2 精确查询由关键词检索承担。

### 14.2 分词与 BM25

`tokenize`：代码标识符按驼峰/下划线/连字符拆词并保留原词（`puschDecode` → `puschdecode` + `pusch` + `decode`）；英文/数字小写化；CJK 按二元组（bigram）切分，不引入分词依赖。

`Bm25Index`：纯 Python BM25（Okapi，k1=1.5, b=0.75），从 chunks.jsonl 构建；落盘只存切块， posting list 加载时重建（万级切块重建在秒级）。

### 14.3 向量

`EmbeddingBackend` Protocol：`name` / `dim` / `embed(texts) -> vectors`（归一化）。内置 `HashEmbedding`：词元哈希投影到固定维 + L2 归一，确定性、可测试；同一索引绑定一个 `embedding_model` 版本，换模型必须重建（10.4.2）。

向量落盘 `vectors.bin`（`array('f')` 顺序块，与 chunks.jsonl 行号一一对应）；查询时全量读入内存算余弦。

### 14.4 检索流程（10.5 裁剪版）

```text
query → tokenize
  → BM25 Top N        ─┐
  → 向量 Top N         ├→ RRF 融合（k=60）
  → 确定性重排：查询中的标识符精确命中加分；同分按 trust_tier（T1>T2>T3）
  → Top K
```

`SearchHit{chunk, score, bm25_rank, vector_rank}`。搜索模式全程不调用模型。

### 14.5 问答（10.6 裁剪版）

- 检索 Top K 组装 `passages.json`（`[S1..Sn]` 编号 + 出处：file:line 或 page_id）；
- 问答任务包沿用 S4 任务包布局：`jobs/ask-<ts>/`（task.md / constraints.md / context/{question.txt,passages.json} / output/）；
- 经 `ModelBackend.run` 生成 `answer.md` + `result.json`（`citations`）；
- **回答校验**：answer.md 中的 `[Sn]` 必须 ⊆ passages 编号；result.citations 同理；`confidence=high` 时至少 2 个独立来源，否则降级；校验失败按修复循环重试（≤3 轮）；
- **拒答**：检索 Top 1 无任何关键词命中且向量分数低于噪声门槛时，不调用模型，直接回答「根据现有资料无法确认」。门槛随索引规模自适应：哈希嵌入的无关余弦是噪声，N 个切块下噪声上限 ≈ √(2·ln N)/√dim，取 1.5 倍（`HybridSearcher.min_vector_score()`）；固定阈值在 3 万块规模下实测失效（噪声漂到 0.39），接入真实嵌入模型后按模型重新标定；
- MockBackend 支持 ask 任务包：模板化组装「直接答案 + 逐条引用」的答案，引用全部来自 passages，作为问答质量地板。

### 14.6 索引存储与一致性（10.8 裁剪版）

`FilesystemIndexStore`：`indices/<repo_id>/i<ts>-<rev8>/{chunks.jsonl,vectors.bin,index.json}` + `current` 指针原子切换；`index.json` 记录 snapshot_id、chunk 数、embedding_model、dim、词表大小。加载时校验：行数 == 向量数、chunk_id 无重复、快照与索引一致。

```text
codingwiki search --repo R "query" [--top-k 10]

```

## 15. S6：真实嵌入与重排（语义检索增强）

### 15.1 目标与非目标

目标：S5 的 `HashEmbedding` 只是词面占位，无语义能力。S6 接入真实嵌入模型（bge-m3）与真实重排模型（bge-reranker-v2-m3），让检索具备同义与跨语言能力，同时保持：

- **默认仍为 HashEmbedding**：CI 与离线环境零依赖可跑，真实模型为可选增强；
- **索引与模型绑定**：`index.json` 记录模型名，换模型强制重建；
- **可降级**：模型缺失时给出明确错误与降级路径，不静默退化。

非目标：不引入向量库（仍为文件索引 + 内存余弦）、不做学习式调参、不改问答协议。

### 15.2 后端协议

```python
class EmbeddingBackend(Protocol):      # 已有，不变
    name: str; dim: int
    def embed(self, texts: list[str]) -> list[list[float]]: ...

class RerankerBackend(Protocol):       # 新增
    name: str
    def score(self, query: str, passages: list[str]) -> list[float]: ...
```

两个实现：

- `BgeM3Embedding`：transformers 直接加载 XLM-R，**CLS pooling + L2 归一**（bge-m3 的 `1_Pooling/config.json` 即 `pooling_mode_cls_token=true`），不依赖 sentence-transformers（其 `modules.json` 引用的 `2_Normalize` 目录在本机模型里缺失）；
- `BgeReranker`：`AutoModelForSequenceClassification`（XLMRobertaForSequenceClassification），`sigmoid(logits)` 作为相关性分。

惰性加载：首次调用才加载权重，构造对象零成本；设备 `auto` 时优先 MPS，其次 CPU。

### 15.3 实测性能（本机 M 系列 CPU，bge-m3 d=1024，568M 参数）

| 项 | 实测 |
|---|---|
| 模型加载 | 17.6s（一次性） |
| 短文本 12 条 | 0.07s（≈6ms/条，batch 32） |
| reranker 3 对打分 | 0.81s（含预热）；相关 0.9898，无关 0.0001/0.0004 |
| `vectors.bin` 体积 | 1024 维 float32 = 4KB/块；3 万块 ≈ 120MB |

索引构建按 1000 块输出一次进度；`--limit` 支持小规模试跑。

### 15.4 检索流程变更

```text
query → tokenize
  → BM25 Top N ─┐
  → 向量 Top N ─┴→ RRF(k=60) → 候选池（rerank_pool，默认 20）
       → [reranker 启用] cross-encoder 重排 → Top K
       → [reranker 关闭] 标识符加权 + trust tier 破平 → Top K
```

`SearchHit` 增加 `rrf_score` 与 `rerank_score` 字段，保留原始融合分以便观察与回归对比；`score` 为重排后的最终排序分（未重排时等于融合分）。

### 15.5 拒答阈值标定（v0.8 重标定，S9-b）

- `HashEmbedding`：沿用统计公式 `1.5·√(2·ln N)/√dim`（无语义模型，噪声主导）；
- `BgeM3Embedding`：**标定值** `retrieval.min_vector_score = 0.595`，按 cuphy-v2 金标准集（56 问）实测分布标定：拒答题 Top1 向量分上界 0.5907（R01；另有 1 道 hard 例 R05=0.665 落在可答题区间内不可分），可答题下界 0.5740（Q23），分隔区间 (0.5907, 0.5999) 取中点。v0.7 的 0.35 为占位值，S9 实测证明对 bge-m3 失效。

判定规则按嵌入后端分两档，由 `HybridSearcher.is_refusal(top)` 统一封装，`AnswerPipeline` 不再自行拼条件：

- **哈希后端**（`min_vector_score` 走公式、无 override）：保持原双条件——Top1 无 BM25 命中**且**向量分低于噪声门槛才拒答。原因：哈希向量无语义，可答题的向量分本身就在噪声区，仅凭向量分判定会把可答题全部误拒；
- **语义后端**（标定值 override 生效）：单条件——Top1 向量分低于标定阈值即拒答。原因：bge-m3 对领域外问题仍会因词面重叠产生 BM25 命中，双条件的第一条在真实模型下恒不成立（S9 实测 4 道拒答题全部漏拒）。

阈值来源必须可追溯：评测报告（`EvalReport.per_question`）记录每题 Top1 的 `vector_score` 与 `bm25_rank`，阈值取「拒答题 Top1 向量分上界」与「可答题 Top1 向量分下界」之间的分隔点，并要求两侧均 ≥85% 指标达标。

### 15.6 索引与配置

`index.json` 的 `embedding_model` 写全名（`hash-embed-v1-d256` / `bge-m3-d1024`）；`_load_searcher` 为每个已有模型名注册工厂，模型缺失时报错并提示「用 --embedding hash 重建」。

配置扩展（`configs/default.yaml` 与 `config/models.py` 同步）：

```yaml
embedding:
  backend: local          # local=真实模型，hash=词面占位
  model_path: ...         # 可被 CODINGWIKI_MODEL_DIR 覆盖
  device: auto            # auto / cpu / mps / cuda
  batch_size: 32
  max_length: 512         # 截断长度；bge-m3 支持 8192，但 CPU 代价高
  dimension: 1024
reranker:
  enabled: true
  model_path: ...
  device: auto
  batch_size: 16
  top_n: 8
retrieval:
  min_vector_score: 0.595
  rerank_pool: 20
```

### 15.7 CLI

```text
codingwiki index build --repo R [--embedding hash|bge-m3] [--model-path P]
                       [--device auto] [--batch-size 32] [--max-length 512] [--limit N]
codingwiki search --repo R --query Q [--top-k 10] [--rerank/--no-rerank] [--rerank-model-path P]
codingwiki ask    --repo R --question Q [--top-k 8] [--rerank/--no-rerank]
```

`--embedding` 缺省读环境变量 `CODINGWIKI_EMBEDDING`，再缺省 `hash`（保证 CI 与离线可跑）。加载索引时按 `index.json` 的模型名自动选择对应后端，命令行参数只影响新建索引。

### 15.8 测试策略

| 层级 | 内容 | 是否需真实模型 |
|---|---|---|
| 配置单元 | embedding/reranker 新字段校验、设备枚举、阈值范围 | 否 |
| 嵌入单元 | 维度、L2 归一、确定性、批处理一致性 | 是（slow） |

| 场景 | 行为 |

## 16. 面向第二、三阶段的接口预留

### 16.1 为什么一阶段就要写这一节

二三阶段不是"再做一套系统"，而是消费一阶段的产物：

- 二阶段（Spec）：读 Wiki 页 + 代码事实 + 快照，产出可追溯的规格 → 依赖**结构化事实查询**与**按范围检索**；
- 三阶段（编码）：按 Spec 改代码、跑构建测试、失败回喂修复 → 依赖**命令执行器**、**补丁/工作树**、**独立验证**。

如果一阶段只按自己方便定接口，二三阶段会被迫改动业务层甚至数据模型。本节把"现在必须留的缝"与"到时才建的东西"分开，避免过度设计。

### 16.2 二三阶段对一阶段产物的硬依赖

| 二/三阶段需求 | 依赖的一阶段能力 | 现状 |
|---|---|---|
| Spec 影响分析（13.6）：文件/接口/调用方/配置/构建/测试 | 符号、调用、配置、构建、测试事实 | ✅ 有数据，缺查询 API（见 16.3-1） |
| 追溯矩阵（13.7）"代码位置必须在当前快照中存在" | 符号存在性校验、快照绑定 | ⚠️ 有数据，缺校验 API |
| 需求文档与 Wiki 同库检索（13.2） | Chunk 多来源、按范围过滤 | ⚠️ 无 filters（见 16.3-2） |
| 编码任务"只改 Spec 列出的文件"（14.6.2） | 路径白名单 + diff | ❌ 无 diff/补丁模型（见 16.4-2） |
| 每任务独立工作树、从快照建分支（14.6.1） | SourceProvider 建工作树 | ❌ 只有 materialize（见 16.3-4） |
| Cline 只改文件、编排器跑命令（14.3） | ModelBackend + **CommandRunner 分离** | ❌ 无 CommandRunner（见 16.3-3） |
| 失败回喂修复（14.5） | 任务包 + 错误包契约 | ✅ 已有（S4 修复循环、S5 errors.json） |
| 独立验证（14.8） | 只读校验器原则 | ✅ 原则成立，模块二阶段新建 |
| 过期标记（7.9/9.14） | PageStatus.STALE 写入逻辑 | ❌ 只有枚举（见 16.3-5） |

### 16.3 必须在一阶段补齐的接口缝（否则二三阶段要改接口）

**1）结构化事实查询 API（`facts/index.py`）**

现状：`FilesystemFactStore` 只有 load/latest/save/cached_file；CLI `facts query` 是字符串过滤，程序无法用。
二三阶段需要：`symbol_by_id`、`symbols_in_module`、`callers_of(symbol_id)`（反向调用图，13.6 的"调用方"）、`tests_for_path`、`assert_symbol_exists(symbol_id, snapshot)`（13.7 校验）、`build_targets_touching(paths)`。
落盘形态不变（仍是 JSON），只在内存建反查表；这是纯新增，不破坏已有调用。

**2）检索范围过滤（`SearchFilters`）**

现状：架构文档 3.3 写了 `Retriever.search(query, filters, top_k)`，但 `HybridSearcher.search()` 只有 `top_k/per_channel`——**文档与代码不一致，本身是缺陷**。
需要：`module`、`file_prefix`、`source_types`、`trust_tiers`、`snapshot_id`、`page_ids`。二阶段"只找某个模块的影响面"、三阶段"只看允许修改的文件"都要用；ACL（10.11）也需要在这里落地为 `allowed_modules`。

**3）命令执行器（`exec/`，只定协议 + 本地实现）**

计划 14.3 明确：**Cline 只改文件，不执行命令**；编译/测试/lint 由编排器执行，输出统一可审计。
需要 `CommandRunner` 协议：`run(spec) -> CommandResult{status, exit_code, stdout, stderr, duration_ms, artifacts}`，仓库配置提供 `configure/compile/incremental/test/lint` 命令与超时（14.7.1）。
一阶段就先落地它的价值：真实仓库的"构建/测试"可以作为事实层的交叉验证；三阶段直接复用，不必改接口。

**4）工作树与分支（SourceProvider 扩展）**

现状：只有 `materialize(repo, revision) -> Path`，会切同一个工作目录。
需要 `create_worktree(repo, revision, path, branch) -> Path` 与 `remove_worktree(path)`；git 用 `git worktree add`，p4 用独立 workspace。三阶段每任务一个工作树，无法靠 materialize 复用同一个目录。

**5）页面生命周期（过期与回滚）**

现状：`PageStatus.STALE` 有枚举无写入；`current` 指针存在但无 `rollback` 命令。
需要：快照 diff 中 deleted/modified 文件 → 标记相关页 stale；`wiki rollback --to <version>`。二三阶段要保证"Spec 引用的现状不是过期页面"。

### 16.4 只需预留、不在阶段一实现

| 能力 | 预留方式 | 实现阶段 |
|---|---|---|
| 补丁/Diff 模型（`Patch`、`FileDiff`） | 三阶段新增 `domain/patch.py`；一阶段只需保证 SymbolFact 的 `path/line/end_line` 与 `blob_sha256` 可定位 | 三阶段 |

| 需求文档切块 | `Chunk.source_type="doc"` 已是字符串，无需改模型 | 二阶段 |
| 独立验证器 | 复用"只读、不改内容"的校验器原则；行为验证与内容校验分开建模块 | 三阶段 |
| ACL 多租户 | 先用 16.3-2 的 `allowed_modules` 过滤；完整 ACL 随部署形态 | 二三阶段 |

### 16.5 明确不做（避免过度设计）

- 不引入向量库/数据库：文件索引 + 内存余弦在 3 万块规模实测可用（约 120MB 内存），二三阶段如有 2000 万行量级再换；

- 不在阶段一建 Spec/任务模型：没有真实 Spec 输入就设计不准，等二阶段用真实需求反推；
- 不允许"模型执行命令"：这是 14.3 的硬边界，一阶段就用协议把二者分开，避免后面拆依赖。

ApiBackend 要点：复用 `TaskPacket`/`BackendResult` 契约；配置取 `model.api.{base_url,model,api_key_env}`；把 task.md + constraints.md + context/* 拼成一次请求，要求返回 JSON；解析失败按 `INVALID_OUTPUT` 进入修复循环；无 key/网络失败抛 `EnvironmentIssue`，不静默退回 mock。

## 18. JobRunner 与日更回流闭环（S10，v0.9 新增）

### 18.1 目标与裁剪

把现有六条单命令串成一条**可日更的回流闭环**，一个入口供 cron 调用（计划 7.7.1：定时=cron/systemd 调 CLI，默认每天 02:00）：

```text
codingwiki run --repo <id|all> [--revision R] [--from stage] [--skip stage]...
               [--backend mock|api] [--app-config P] [--config-dir D]
```

阶段顺序（计划 5.4 裁剪到一阶段已交付能力）：`sync → facts → wiki → verify → publish → index`。

明确不做（裁剪决策）：
- **不做守护进程调度器**：cron 调 CLI 即为定时触发，`run` 是唯一入口；
- **不做数据库队列/状态机持久化**：任务记录就是 JSON 审计文件（计划 504 可审计的最小实现）；
- **不做 runner 级重试**：模型阶段（generate/ask）已有内部 3 轮修复循环，确定性阶段重试无意义；
- **失败不影响旧版本**不靠 runner 保证：发布门禁 + current 指针机制（S4/S7 已交付）保证中途失败时线上版本不变，runner 只保证失败后不清理、不回滚任何产物。

### 18.2 编排层 `pipeline/`（新分层落地）

分层规则的「编排层 pipeline/」在本阶段首次落地：`cli → pipeline → 能力层`。CLI 瘦身为「解析参数 + 打印」，阶段逻辑下沉；CLI 现有辅助函数（`_resolve_snapshot` / `_facts_workdir` / `_assert_workdir_revision` / `_load_facts_or_raise` / `_wiki_workdir` / `_resolve_wiki_backend`）迁入 pipeline，CLI 反向 import（入口层依赖编排层，方向合规）。

| 模块 | 职责 |
|---|---|
| `domain/job.py` | `JobRecord` / `StageResult` 纯模型（frozen Pydantic，无 I/O） |
| `pipeline/lock.py` | `RepoLock`：per-repo 文件锁（`O_CREAT\|O_EXCL`），`.codingwiki/locks/<repo_id>.lock`，内容为 pid+时间戳+主机名；持有进程已死判定为陈旧锁可安全接管，内容不可解析视为存活报错 |
| `pipeline/stages.py` | 六个阶段函数 `stage_*(ctx: JobContext) -> str`（返回 summary）；`JobContext` 携带 repo 配置、参数与跨阶段产物（snapshot/facts） |
| `pipeline/runner.py` | `JobRunner`：顺序执行、`--from` 断点进入、`--skip` 跳过（记 skipped）、失败即停（后续记 skipped）、每阶段计时、`JobRecord` 落盘 `.codingwiki/jobs/<repo>/<ts>-<job_id>.json` |

### 18.3 失败语义与退出码

- 任何阶段抛异常 → 该阶段 `failed`，其后全部 `skipped`，job `status=failed`，退出码沿用异常的 `ExitCode`；
- `wiki` 阶段有页面生成失败 → 视为阶段失败（不进入 verify/publish，宁可发不了版也不发坏版本）；
- `--repo all`：遍历 `configs/repos/*.yaml` 逐仓独立执行，单仓失败不影响其他仓，任一仓失败则总退出码非 0；
- `RepoConfig` 新增 `enabled: bool = True`（计划 5172）：`--repo all` 跳过 `enabled=false` 的仓库。

### 18.4 锁规则

锁粒度 = 仓库。`run` 全程持锁；同一仓库并发触发时第二个进程立即失败（报持有者 pid 与启动时间），不等待、不排队——日更场景宁可失败重跑也不要并发写坏快照。

## 19. 站点覆盖率看板（S11，v0.10 新增）

### 19.1 目标与裁剪

计划 9.13（质量看板）裁剪到一阶段可机械计算项，产出两处：

1. **站点看板页**：发布时生成 `dashboard.html` 进入版本站点（导航入口「看板」），与页面同一次发布、同一个版本目录——看板不是独立服务，是版本的静态产物；
2. **CLI `wiki coverage`**：同一数据源的文本矩阵，供终端/CI 快速查看。

看板数据（`DashboardData`，`domain/dashboard.py` 纯模型）：

| 数据 | 来源 | 计划依据 |
|---|---|---|
| 版本/快照/发布时间、页面状态分布、证据总数 | 当前版本 index.json | 9.13 |
| 覆盖率矩阵（模块 × C0/C1/C2/C3） | facts + 版本 deps.json | 4.6.2 |
| 检索评测指标 | `.codingwiki/evals/<repo>/` 最新报告 | 9.13 |
| 最近任务记录 | `.codingwiki/jobs/<repo>/` 最新 JSON | 9.13 |

明确不做：人工审核状态、用户反馈、下次更新时间（无调度器配置可读，二阶段随 S8/调度补）、看板下钻到缺口任务的自动生成（缺口清单已在矩阵中列出，任务生成留二阶段）。

### 19.2 覆盖深度口径（矩阵每一格怎么算，全部确定性）

| 深度 | 基数 | 分子（covered） |
|---|---|---|
| C0 已登记 | 快照 manifest 发现的文件（in_scope + excluded） | in_scope 文件（excluded 也已登记，登记率恒 100%，矩阵给出绝对数验证不变量） |
| C1 已说明 | facts 在范围文件 | 被任一已发布页面 deps.files 引用的文件 |
| C2 已说清接口 | 公开符号（`is_public_symbol`，与生成侧同一谓词） | 符号所在文件是某 interface 页的 deps 文件 |
| C3 已说清流程 | main/python_main 入口（按目录去重，与流程页规划同规则） | 入口文件是某 flow 页的 deps 文件 |

矩阵按 `FileFacts.module` 分组出模块行，另加 `total` 行；缺口 = 每行的未覆盖基数（计划 4.6.2 的下钻起点，任务自动生成留二阶段）。

### 19.3 数据流与分层

```text
wiki publish / stage_publish
  → build_dashboard(repo_id, facts, store)   # publish/dashboard.py，只读
      ├─ store.version_index / load_version_deps
      ├─ FilesystemSnapshotStore.manifest（C0 基数）
      ├─ eval.load_previous_report（最新评测，缺则 None）
      └─ jobs 目录最新记录（缺则 None）
  → store.publish(..., dashboard=...)
      → build_site(..., dashboard=...) 写 dashboard.html + 导航入口
```

`publish → generate.modules`（复用 `is_public_symbol` 纯函数）是能力层内部的纯函数复用，无环、无状态；除此以外看板不新增跨层依赖。`wiki coverage` CLI 与站点看板消费同一个 `build_dashboard`，两处数字不可能不一致。

### 19.4 一阶段覆盖口径决策（2026-11-07）

cuphy 实测 C1 38%、C2 71%、C3 14%，低于计划 4.3 的第一阶段 MVP 门槛（≥95%/≥95%/≥80%）。根因是页面粒度：S6.5 经确认的裁剪把页面定为模块/接口/流程聚合页（总量 50–120 页），91 页对 1,019 个文件天然无法逐文件覆盖；interface 页 24 页上限使 util/ldpc 一页聚合 4,799 个公开符号。

**决策：一阶段接受聚合页粒度口径为交付形态**，C0 保持 100% 登记不变量；把「逐文件说明（C1）/ 逐接口成页（C2）/ 全量入口流程（C3）」的 95%/95%/80% 目标移入二阶段，以 S11 矩阵的缺口清单为下钻起点扩页。该决策同时记入验收报告 §4.3/§6，不改变 C0–C3 的矩阵计算口径（看板仍按原口径如实报数）。
