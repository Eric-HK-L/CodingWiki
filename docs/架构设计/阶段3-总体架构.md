# 阶段三总体架构：Spec → 自动编码与测试

> 版本：v1.0（2026-10-30）
> 定位：阶段三的实施基线。跨阶段契约见 `总体架构-三阶段.md`；业务要求见
> `docs/CodingWiki-项目开发计划.md` 第 14 章。
> 前置：阶段二的已批准 Spec、阶段一的快照与 `CommandRunner`、可用的模型后端。

## 1. 目标与边界

目标：从已批准 Spec 生成小步编码任务，在隔离工作树中由模型改文件，由编排器执行构建/测试，失败回喂修复，独立验证后交付补丁。

硬边界（来自 14.3）：**模型只改文件，绝不执行命令**。命令执行、diff 检查、验证全部由编排器完成。

不做：对不可靠测试强行自动化、自动合并高风险改动到主干、对所有需求零人工。

## 2. 前置条件（14.2）

| 条件 | 校验方式 | 不满足时 |
|---|---|---|
| Spec 已批准且无 blocking 问题 | `specs/<id>/state.json` | 拒绝运行 |
| 快照可复现 | `snapshots/<repo>/<rev>.json` | 拒绝运行 |
| 构建/测试命令已配置 | `configs/repos/<repo>.yaml` 的 `build/test/lint` 段 | 拒绝运行并列出缺失项 |
| 工作树磁盘充足 | 预检阈值（可配置，默认 20 GB） | 拒绝并提示清理 |
| 模型后端可用 | 探活一次 | 拒绝（不静默降级到 mock） |

## 3. 架构

```text
已批准 Spec
   │ TaskDecomposer（Spec → T-…，含验收测试与依赖序）
   ▼
┌──────────────────── CodingRunner ────────────────────┐
│ 1 准备聚焦上下文（文件/符号/测试/规范/相关 Wiki 页）    │
│ 2 ModelBackend 修改工作树（只改文件，返回 diff）       │
│ 3 PatchGuard 检查 diff（路径白名单/行数/文件数/禁止项） │
│ 4 CommandRunner 运行 lint + 编译（增量目标优先）        │
│ 5 CommandRunner 运行测试（fast → full）               │
│ 6 失败 → 结构化错误包 → 回步骤 2（轮次上限可配）        │
│ 7 通过 → IndependentVerifier 复核（非同一模型）         │
│ 8 回归测试（受影响的既有测试）                          │
│ 9 产出补丁 + 报告（PR 描述 / 交付包）                   │
└──────────────────────────────────────────────────────┘
```

## 4. 领域模型（`domain/patch.py` / `domain/coding.py`，继承 `CodeWikiModel`）

```python
class CodedTask(CodeWikiModel):
    id: str                  # T-<spec_id>-<n>
    spec_id: str
    requirement: str         # R-…
    title: str
    files_allowed: list[str] # 白名单（来自 Spec）
    acceptance_tests: list[str]
    depends_on: list[str]
    constraints: list[str]

class FileDiff(CodeWikiModel):
    path: str
    change: str              # added/modified/deleted
    added_lines: int = 0
    removed_lines: int = 0
    binary: bool = False
    whitespace_only: bool = False

class Patch(CodeWikiModel):
    patch_id: str            # P-<run_id>
    run_id: str
    files: list[FileDiff]
    diff_text: str           # unified diff，可回放应用

class CommandResult(CodeWikiModel):
    kind: str                # lint / compile / test
    status: str              # ok / failed / timeout / error
    exit_code: int
    duration_ms: int
    stdout_tail: str         # 截断后保留关键段
    stderr_tail: str
    artifacts: list[str]     # 报告路径（如 junit xml / 编译日志）

class TestReport(CodeWikiModel):
    total: int
    passed: int
    failed: int
    skipped: int
    failures: list[str]      # 结构化失败项（文件:测试名:原因）

class CodedRun(CodeWikiModel):
    run_id: str              # RUN-<task_id>-<n>
    task_id: str
    status: str              # succeeded / failed / escalated
    rounds: int
    patch: Patch | None
    build: list[CommandResult]
    tests: TestReport | None
    guard: list["GuardViolation"]
    cost: dict[str, int]     # tokens_in / tokens_out / duration_ms
```

## 5. 任务分解（14.4）

规则：一任务一件事；改动 ≤ 300 行、≤ 3 文件；有明确输入/输出/验收测试；任务间有依赖序；可独立回滚。

分解输入：Spec 的追溯矩阵（需求→设计→代码→测试）。分解器**必须**为每个任务绑定：
- `files_allowed`（来自影响分析，不是模型自由选择）；
- `acceptance_tests`（来自 Spec 测试计划）；
- `constraints`（编码规范 + 术语表 + 禁止引入依赖）。

## 6. 编码循环（14.5）

| 轮次 | 输入 | 输出 | 退出条件 |
|---|---|---|---|
| 1 | 任务包（上下文 + 约束） | 文件修改 + `result.json` | diff 通过护栏 |
| 2..N | 上一轮 `errors.json`（结构化失败项） | 修改 | 构建与测试全绿，或轮次耗尽 |
| 结束 | — | `CodedRun` | 成功交付补丁；失败升级人工 |

关键：**失败信息结构化**，不是把原始日志整段塞回模型。`CommandResult.stdout_tail` 经解析器转成 `{file, line, code, message}` 列表。

## 7. 补丁协议与工作区（14.6）

| 项 | 规则 |
|---|---|
| 工作树 | 每任务一个 `worktrees/<task_id>/`，从快照建分支 `cw/<task_id>` |
| 成功 | 保留分支与补丁，等待人工合并 |
| 失败 | 丢弃工作树（保留 diff 与日志用于分析） |
| 允许路径 | Spec `files_allowed` + 同模块测试文件 + Spec 声明的头文件 |
| 禁止 | 构建脚本、CI、密钥、生成文件、第三方目录、删测试、改断言、新依赖、网络、二进制 |
| Diff 检查 | 行数/文件数上限、无二进制、无整文件换行符变化、无纯格式化、无大段注释代码、无调试输出、无未说明 TODO、无密钥模式 |

## 8. 构建与测试编排（14.7）

仓库配置（`configs/repos/<repo>.yaml` 扩展）：

```yaml
build:
  configure: "cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug"
  compile: "cmake --build build -j 8"
  incremental: "cmake --build build -j 8 --target <target>"
  timeout_s: 1800
test:
  fast: "ctest --test-dir build -R '<pattern>' --output-on-failure"
  full: "ctest --test-dir build --output-on-failure"
  timeout_s: 3600
  report_format: junit
lint:
  command: "clang-tidy …"
  timeout_s: 600
```

`CommandRunner` 协议：`run(spec: CommandSpec) -> CommandResult`；实现 `LocalCommandRunner`（subprocess + 超时 + 输出截断 + 报告解析）。三阶段的编排器与阶段一的事实交叉验证共用它。

## 9. 独立验证器（14.8）

与编码模型不同来源的检查，全部机械化：

| 检查 | 判定 |
|---|---|
| 补丁仅触碰白名单 | 违反即失败 |
| 构建与测试全绿 | 任一失败即失败 |
| 验收测试确实覆盖需求 | 用例名/断言对照 Spec 验收标准 |
| 无回归 | 受影响既有测试全部通过 |
| 无跳过/禁用测试 | 检测 `skip`/`xfail`/注释断言 |
| 无调试残留 | 关键词与模式扫描 |
| 报告可复现 | 使用快照 + 补丁重放一次 |

## 10. 护栏（14.9）

路径越界、命令注入、网络访问、密钥读取、大范围格式化、删除测试、修改断言、引入依赖——命中任一项即中止并记录 `GuardViolation`。护栏是**编排器**的职责，不依赖模型自觉。

## 11. 失败处理与升级（14.10）

| 情形 | 处理 |
|---|---|
| 轮次耗尽 | 标记 `escalated`，输出「已尝试/已排除/建议下一步」 |
| 环境失败（编译工具缺失/磁盘满） | 不重试，环境错误退出码 |
| 模型不可用 | 中止，不降级 |
| 连续 N 任务失败 | 熔断，停止本次运行并告警 |

## 12. 指标（14.11）

任务成功率、平均轮次、构建时长、测试时长、token 成本、护栏命中率、回归引入率。全部落 `runs/<repo>/<run_id>/report.json`。

## 13. 存储与 CLI

```text
.codingwiki/worktrees/<task_id>/                 # 工作树（任务结束按结果保留或丢弃）
.codingwiki/runs/<repo>/<run_id>/
├── patch/<patch_id>.diff
├── build/  test/  lint/                        # 命令输出与报告
└── report.json                                 # 状态、轮次、成本、指标
```

```text
codingwiki code plan   --repo R --spec F-…
codingwiki code run    --repo R --spec F-… [--task T-…] [--max-rounds 5]
codingwiki code status --repo R --run RUN-…
codingwiki code apply  --repo R --run RUN-…    # 把补丁应用到指定分支（人工确认后）
```

## 14. 测试策略

| 层级 | 内容 |
|---|---|
| 模型单元 | 任务分解规则、`Patch`/`FileDiff` 校验、状态机 |
| 护栏单元 | 白名单、行数上限、禁止项检测（每条正例/反例） |
| 执行器单元 | `LocalCommandRunner` 超时、退出码、输出截断、junit 解析 |
| 循环集成 | 假模型 + 假构建（注入编译失败 → 修复成功 / 轮次耗尽） |
| 端到端 | fixture 仓库：Spec → 任务 → 补丁 → 构建测试 → 报告 |
| 回归 | 同一 Spec 重放两次，补丁确定性（除时间戳） |

## 15. 验收清单（对齐 14.14）

- [ ] 每任务一个独立工作树，从快照建分支；
- [ ] 模型只改文件，全部命令由编排器执行；
- [ ] 越界路径/新依赖/二进制/改测试断言被护栏拦截；
- [ ] 编译或测试失败能结构化回喂并重试；
- [ ] 轮次耗尽给出可操作报告，不盲目继续；
- [ ] 独立验证覆盖"无回归/无跳过/无调试残留"；
- [ ] 补丁可重放，结果可复现；
- [ ] 成本与时长落盘可统计；
- [ ] 失败不污染主干（工作树丢弃，补丁仅保留分析）。

## 16. 明确不做

- 不做自动合并到主干（必须人工确认）；
- 不做跨仓库批量改写；
- 不在测试不可靠时强行自动化（先修测试）；
- 不引入容器编排复杂度：首个版本用本机 worktree + 进程隔离，容器化留后续。
