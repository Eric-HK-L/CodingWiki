# 阶段二总体架构：需求文档 → 开发 Spec

> 版本：v1.0（2026-10-30）
> 定位：阶段二的实施基线。跨阶段的统一实体/ID/存储/接口边界见 `总体架构-三阶段.md`；
> 业务要求见 `docs/CodingWiki-项目开发计划.md` 第 13 章。
> 前置：阶段一的 Wiki 模块页、事实库、快照、索引已可用（S6.5/S7 完成后）。

## 1. 目标与边界

目标：把「Wiki + 新功能需求文档」变成可交给编码阶段执行的开发规格（Spec）。

Spec 必须满足：需求可编号可测试、现状有依据、方案有理由、影响范围明确、测试计划可执行、任务拆得足够小、每条需求可追溯到代码与测试、不明确处明确列为问题。

边界：不替代产品经理决定"做什么"，不替代架构师做技术决策，不保证一次生成完美（必须人工评审），不评价需求文档本身质量。

## 2. 输入与前置

| 输入 | 格式 | 必需 | 来自 |
|---|---|---|---|
| 需求文档 | Markdown | 是 | 用户提供 |
| Wiki 页面 | 阶段一产物 | 是 | `publish/store.py`（模块页/接口页/流程页） |
| 代码事实 | `RepoFacts` | 是 | `facts/`（含反查 API，S7） |
| 快照 | `repo@rev` | 是 | `snapshot/` |
| 编码规范 / 测试规范 / 术语表 | Markdown | 否 | 用户提供或 Wiki 术语页 |

前置校验（缺一即拒绝生成，不降级）：

1. 快照与 Wiki 当前版本一致（`VersionIndex.snapshot_id == facts.snapshot_id`）；
2. 模块页存在且非 stale；
3. 事实反查 API 可用（`callers_of` / `tests_for_path` / `assert_symbol_exists`）。

## 3. 数据流

```text
需求文档 ──解析──▶ RequirementDoc(需求条目 R-…)
                      │
                      ├─▶ 检索现状（Wiki 页 + 事实 + 代码块）
                      ├─▶ 影响分析（模块/文件/接口/调用方/配置/构建/测试）
                      ├─▶ 方案生成（≥1 候选 + 取舍理由）
                      ├─▶ Spec 组装（13.3 模板，逐节填充）
                      ├─▶ 自动校验（13.8 十条规则）
                      └─▶ 人工评审 → approved / needs-info / rejected
                                  │
                                  ▼
                            specs/<spec_id>/（供三阶段消费）
```

## 4. 领域模型（`domain/spec.py`，继承 `CodeWikiModel`）

```python
class Requirement(CodeWikiModel):
    id: str                  # R-<spec_id>-<n>
    text: str                # 需求原文
    acceptance: list[str]    # 可执行验收标准
    source: str              # 文档位置（章节/行号）

class RequirementDoc(CodeWikiModel):
    doc_id: str
    path: str
    title: str
    requirements: list[Requirement]
    ambiguities: list[str]   # 文档自身的不明确处

class ImpactItem(CodeWikiModel):
    dimension: str           # module/file/interface/caller/config/build/test/perf/security/compat
    summary: str
    refs: list[str]          # symbol_id / page_id / file:line，必须可解析

class ImpactAnalysis(CodeWikiModel):
    items: list[ImpactItem]

class TraceLink(CodeWikiModel):
    requirement: str         # R-…
    design_sections: list[str]
    code_refs: list[str]     # symbol_id（必须存在于快照）
    tests: list[str]         # 测试用例/文件
    tasks: list[str]         # T-…

class OpenQuestion(CodeWikiModel):
    id: str
    question: str
    blocking: bool           # 阻断项必须在 approved 前关闭
    answer: str = ""

class Spec(CodeWikiModel):
    spec_id: str             # F-<yyyymmdd>-<seq>
    snapshot_id: str
    status: SpecStatus       # draft / needs-info / approved / rejected
    requirements: list[Requirement]
    impact: ImpactAnalysis
    traces: list[TraceLink]
    open_questions: list[OpenQuestion]
    body_markdown: str       # 13.3 模板正文
```

## 5. 生成流水线（`pipeline/spec.py`）

| 步骤 | 输入 | 输出 | 失败处理 |
|---|---|---|---|
| 1 需求抽取 | 需求文档 | `RequirementDoc` | 无编号/无验收标准 → 记为 ambiguity，不阻断抽取 |
| 2 现状检索 | 需求关键词 | 相关 Wiki 页 + 事实 + 代码块 | 无命中 → 生成 blocking OpenQuestion |
| 3 影响分析 | 需求 + 事实 | `ImpactAnalysis` | 任一 `refs` 无法解析 → 校验失败 |
| 4 方案生成 | 影响分析 + 规范 | 候选方案 + 取舍 | 模型输出不合 schema → 修复循环 ≤3 轮 |
| 5 Spec 组装 | 上述全部 | `Spec.body_markdown` | 缺章节必须写「不适用 + 原因」 |
| 6 自动校验 | Spec | 阻断/警告/信息 | 阻断项不过不得进入评审 |
| 7 人工评审 | Spec + 校验报告 | approved/rejected | 记录 reviewer |

模型调用走 `ModelBackend`（与阶段一同一契约）。任务包结构：`jobs/spec/<repo>/<ts>-<spec_id>/`，context 内含 `requirements.json`、`wiki_pages.json`、`impact_seed.json`、`glossary.json`。

## 6. 影响分析实现（13.6 十维度 → 数据来源）

| 维度 | 来源 API | 备注 |
|---|---|---|
| 模块 | `symbols_in_module` + 模块页 | 模块边界来自 facts 的 module 分组 |
| 文件 | 符号索引 | 预计修改文件必须给出依据 |
| 接口 | 公共符号（可导出可见性） | 签名变化要标注 breaking |
| 调用方 | `callers_of(symbol_id)` | 反向调用图，S7 提供 |
| 配置 | `config_facts` | 键与读取点 |
| 构建 | `build_targets_touching(paths)` | 目标与依赖 |
| 测试 | `tests_for_path(path)` | 需新增/修改的测试 |
| 性能/安全/兼容 | 规则库 + 关键路径 | 无依据时写「未评估」而非编造 |

## 7. 追溯矩阵与校验（13.7 / 13.8）

追溯链：`R → 设计章节 → 代码位置(symbol_id) → 测试 → 任务 T`。

校验规则（全部机械化，`verify/spec_rules.py`）：

| 规则 | 判定 |
|---|---|
| 需求覆盖 | 文档中每条需求都有编号且被 Spec 覆盖 |
| 验收标准 | 每条功能需求 ≥ 1 条可执行验收 |
| 代码出处 | 「现状/影响」结论均有引用，且 `symbol_id` 在快照中存在 |
| 追溯完整 | 需求/任务/测试三方无孤立节点 |
| 任务大小 | ≤ 300 行、≤ 3 文件、单一目标 |
| 测试计划 | 每条验收至少 1 个测试用例 |
| 开放问题 | blocking 未关闭 → 阻断 approved |
| 术语一致 | 与 Wiki 术语页一致 |
| 安全/回滚 | 涉及输入/权限/配置的需求须有对应章节 |

## 8. 存储与 CLI

```text
.codingwiki/specs/<repo>/<spec_id>/
├── spec.md          # 人读正文（站点可渲染）
├── trace.json       # 追溯矩阵（机器校验）
├── state.json       # 状态、评审人、时间、快照
└── jobs/            # 生成过程中的任务包与模型输出（可回放）
```

```text
codingwiki spec generate --repo R --doc path/to/req.md [--max-rounds 3]
codingwiki spec check    --repo R --spec F-20261030-01
codingwiki spec review   --repo R --spec F-… --status approved --reviewer <name>
codingwiki spec list     --repo R
```

## 9. 与相邻阶段的接口

| 方向 | 接口 | 约束 |
|---|---|---|
| ← 阶段一 | `WikiStore.load_published_pages`、`FactIndex` 查询、`Retriever.search(filters)` | 不得直接解析 Markdown 文件 |
| → 阶段三 | `specs/<spec_id>/spec.md` + `trace.json` | 三阶段只读落盘产物，不读二阶段内存对象 |
| 共用 | `ModelBackend`、校验器只读原则、ID 体系 | 与阶段一一致 |

## 10. 测试策略

| 层级 | 内容 |
|---|---|
| 模型单元 | `Spec`/`TraceLink` 校验、ID 生成、状态机非法迁移 |
| 规则单元 | 13.8 十条规则，每条正例/反例 |
| 流水线集成 | fixture 需求文档 → Spec → 校验 → 评审状态流转 |
| 追溯闭合 | 人为删掉一条测试/任务 → 校验必须报孤立节点 |
| 端到端 | CLI generate → check → review，失败路径退出码 |

## 11. 验收清单

- [ ] 需求文档每条需求被编号且覆盖；
- [ ] 影响分析十个维度均有内容或明确「未评估」；
- [ ] 所有代码引用可在当前快照解析；
- [ ] 追溯矩阵无孤立需求/任务/测试；
- [ ] 每条验收标准至少一个测试用例；
- [ ] blocking 开放问题关闭后才能 approved；
- [ ] Spec 正文可被站点渲染、无占位语；
- [ ] 生成过程可回放（任务包与模型输出落盘）；
- [ ] 校验失败不覆盖已批准 Spec。

## 12. 明确不做

- 不自动决定需求优先级或产品取舍；
- 不生成代码（那是阶段三）；
- 不对需求文档做语义纠错，只标注问题；
- 不引入独立数据库：Spec 以文件落盘，量级远小于代码索引。
