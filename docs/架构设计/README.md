# 架构设计文档地图

本目录是 CodingWiki 的设计基线。**代码与文档不一致时，以本目录为准并修文档；文档先于代码。**

## 1. 文档清单与定位

| 文档 | 定位 | 什么时候看 |
|---|---|---|
| `总体架构-三阶段.md`（v1.0） | 跨阶段唯一权威：实体与 ID、存储布局、组件映射、依赖规则、接口冻结策略、回流闭环 | 任何跨阶段改动、新增模块前 |
| `阶段1-总体架构.md`（v0.7） | 阶段一实施细节：快照/事实/Wiki/检索/问答，第 17 节定义**人可读 Wiki 的交付形态** | 做阶段一功能时 |
| `阶段2-总体架构.md`（v1.0） | 阶段二实施细节：需求 → Spec 的模型、流水线、影响分析、追溯与校验 | 做 Spec 生成时 |
| `阶段3-总体架构.md`（v1.0） | 阶段三实施细节：任务分解、编码循环、补丁协议、构建测试、独立验证、护栏 | 做自动编码时 |
| `../CodingWiki-项目开发计划.md` | 需求与验收基线（背景、约束、每章验收清单、实施计划、成本） | 确认「要做什么」与验收口径 |
| `../开发记录/阶段1-S*.md` | 每个小阶段的交付证据：设计点、测试数、真实仓库结果、问题修复表 | 验收与追溯决策 |

## 2. 阅读顺序

1. **新人**：`总体架构-三阶段.md` §1–§6（流水线与契约）→ `阶段1-总体架构.md` §1–§4 → 计划第 1–4 章（为什么这样做）。
2. **接一阶段开发**：`阶段1-总体架构.md` 全文 + §16（接口缝）+ §17（输出形态），再看计划第 7–11 章。
3. **接二阶段**：`阶段2-总体架构.md` + 计划第 13 章 + 一阶段 §16.3 的 `FactIndex` 与检索过滤。
4. **接三阶段**：`阶段3-总体架构.md` + 计划第 14 章 + 一阶段 §16.3 的 `CommandRunner` 与 worktree。

## 3. 速查：ID 与目录

| 实体 | 规则 | 落盘位置 |
|---|---|---|
| 快照 | `<repo>@<rev>` | `snapshots/<repo>/<rev>.json` |
| 符号 | `<path>::<qualified>@<line>` | `facts/<repo>/<rev>.json` |
| 页面 | `<type>/<path>/<symbol>` | `wiki/<repo>/versions/<ver>/pages/` |
| 证据 | 页内 `E<n>` | 页面「出处」段 |
| 资料 | 问答内 `S<n>` | `jobs/ask/.../passages.json` |
| 需求 | `R-<spec>-<n>` | `specs/<repo>/<spec>/trace.json` |
| Spec | `F-<yyyymmdd>-<seq>` | `specs/<repo>/<spec_id>/` |
| 任务 | `T-<spec>-<n>` | Spec `trace.json` |
| 运行 | `RUN-<task>-<n>` | `runs/<repo>/<run_id>/` |
| 补丁 | `P-<run_id>` | `runs/<repo>/<run_id>/patch/` |

规则：页内/问答内的局部编号**不落盘为全局引用**；任何跨阶段引用带快照（`R1 @ S2`）。

## 4. 维护规则

1. 开工前先改文档、再写代码；先把要改的章节改好，代码照着实现。
2. 实现中发现设计缺口 → 先改文档，再改代码；不得只改代码。
3. 新增模块必须归入某一层的某一节（总体 §4 组件映射），不允许「先写再找位置」。
4. 任何接口签名变更 → 同步三份阶段文档 + 总体架构 §6 冻结表。
5. 每个小阶段结束在 `../开发记录/` 补一份记录，格式固定（见该目录首篇）。
